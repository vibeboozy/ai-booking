## О проекте

TripVibe — платформа бронирования жилья. Приоритеты: скорость, прозрачность цен, визуальная привлекательность, минимум трения в UX.

Стек: Next.js 15 (App Router), TypeScript (strict), Tailwind CSS, Prisma + PostgreSQL, NextAuth.js, Zod, Vercel AI SDK.

Ключевые принципы:
- URL-driven UI — фильтры и состояние поиска синхронизируются с query-параметрами (?city=...&checkIn=...).
- Server-first data — чтение через Server Components и Route Handlers; мутации через Server Actions.
- Transparent pricing — итоговая цена на чекауте включает все сборы явно, без скрытых комиссий.
- Mock payment — оплата имитируется (POST /api/bookings/mock-pay), интерфейс готов к замене на Stripe.

Основной пользовательский флоу: поиск → фильтрация → карточка объекта → чекаут → профиль (трипы) → отзыв после завершённой поездки.

## Модульная архитектура (КРИТИЧНО)

Проект разделён на 5 независимых модулей в src/modules/:

| Модуль    | Путь              | Ответственность                                      |
|-----------|-------------------|------------------------------------------------------|
| search    | src/modules/search    | Поиск, автокомплит, фильтры, ListingCard (preview)   |
| listing   | src/modules/listing   | Страница объекта, галерея, карта, календарь, ИИ-Консьерж |
| booking   | src/modules/booking   | Чекаут, расчёт цены, mock-оплата, создание Booking   |
| profile   | src/modules/profile   | Профиль, трипы, избранное (FavoriteButton)           |
| reviews   | src/modules/reviews   | Отзывы, рейтинги, агрегация                          |

Общий код — только в src/shared/ (типы, UI-примитивы, утилиты, константы, Zod-схемы) и src/lib/ (Prisma, auth, AI).

### Правила модульных границ

1. Модули MUST быть независимыми. Каждый модуль владеет своей директорией, своими API routes, компонентами, хуками и репозиторием.
2. Модули MUST NOT пересекаться: не дублируй логику другого модуля, не правь файлы внутри чужого модуля, не добавляй фичи в чужую зону ответственности.
3. Импорты между модулями — ТОЛЬКО через публичный API: src/modules/{module}/index.ts.
   Запрещено: import from '@/modules/booking/components/CheckoutForm'
   Разрешено: import { PriceBreakdown } from '@/modules/booking'
4. Запрещены прямые импорты внутренних файлов чужого модуля (components/, hooks/, *.repository.ts и т.д.).
5. Каждый файл MUST содержать якорную разметку (ANCHOR, PURPOSE) — см. src/ANCHORS.md.

### Межмодульные изменения — через задачу на коммуникацию

Если для выполнения задачи нужно изменить код, типы, API или контракт в ДРУГОМ модуле:

- НЕ вноси изменения в чужой модуль самостоятельно.
- НЕ обходи границы «навсегда» через дублирование или хаки в своём модуле.
- Сформулируй задачу для коммуникации между модулями. Задача MUST содержать:
  - целевой модуль и владельца (Dev A–E из semantic_graph.xml);
  - что именно нужно изменить (файл, экспорт, API, контракт);
  - зачем это нужно (контекст твоей задачи);
  - ожидаемый публичный интерфейс (тип, пропсы, endpoint).
- В своём модуле работай только с уже экспортированным публичным API. Если API недостаточно — опиши требуемое расширение в задаче и используй временные заглушки только если это явно согласовано.

Пример задачи:
«Модуль booking → модуль listing (Dev B): нужен экспорт поля maxGuests в ListingDetail для валидации на чекауте. Контекст: ограничение гостей на форме бронирования. Ожидаемый контракт: ListingDetail.maxGuests: number.»

### Интеграционные контракты

Межмодульное взаимодействие — только через задокументированные контракты (semantic_graph.xml, data_models.md):
- search-params — city, checkIn, checkOut, guests, фильтры; парсинг через shared parseSearchParams / buildSearchUrl.
- listing-preview — минимальный набор полей для карточек (search, profile).
- price-breakdown — calculateTotalPrice — единственный источник расчёта цены.
- favorite-button — FavoriteButton экспортируется из profile; search и listing только импортируют.
